**`validation-exception.factory.ts`:** the `exceptionFactory` for the global `ValidationPipe`. It turns class-validator's `ValidationError[]` into

- One `details` entry per field: `{ field, message }`.

**`error-body.ts`:** a pure function `toErrorBody(exception: unknown, path: string, now = new Date())` that returns `{ statusCode, body }`. The body has the shape above, with `details` only when present. The rules, in order:

| Exception | Status | Code | Message | Details |
|---|---|---|---|---|
| `HttpException` whose response object has a string `code` | `getStatus()` | that code | its `message` | its `details`, if an array |
| other `HttpException` | `getStatus()` | by status: 400 `VALIDATION_FAILED`, 401 `NOT_AUTHENTICATED`, 403 `FORBIDDEN_ROLE`, 404 `NOT_FOUND`, 409 `CONFLICT`, any other 4xx `REQUEST_FAILED`, 5xx `INTERNAL_ERROR` | the response's `message` (an array joined with `; `), else `exception.message` | none |
| object with `code === 11000` (Mongo duplicate key) | 409 | `CONFLICT` | `Duplicate value` | one per key of `keyValue`: `{ field, message: 'already exists' }` (omit if no `keyValue`) |
| Mongoose `Error.ValidationError` | 400 | `VALIDATION_FAILED` | `Validation failed` | one per key of `errors`: `{ field: key, message: errors[key].message }` |
| Mongoose `Error.CastError` | 400 | `VALIDATION_FAILED` | `Invalid value` | `[{ field: path, message: 'invalid value' }]` |
| anything else | 500 | `INTERNAL_ERROR` | `Internal server error` | none |

`timestamp` is `now.toISOString()`. `path` is the argument.

## Context you need

**Allowed calls** (`docs/database/data-model.md` §6.1): payments calls nobody (it uses the port). flights and hotels call reference-data and storage. accounts and fx call reference-data. itineraries calls reference-data, fx and storage. blog calls storage. admin calls audit. flight-bookings and hotel-bookings call payments.

**Payments rules** (`docs/ai/skills/travel-platform/references/bookings-payments.md` §4, §6, §7):
- Payments never writes a booking, and bookings never call Stripe.
- `POST /api/payments` checks the booking through the port: it belongs to the user, is `pending_payment`, and `holdExpiresAt > now`.
- On cancellation, the booking module calls `PaymentsService.refund(...)` after its commit, and only if the refund amount is > 0.
- One refund per booking: `refunds` has a unique index on `{ bookingType, bookingId }`.
- Reasons: `user_cancellation`, `provider_cancellation`, `late_payment` (a full refund).
- The Stripe PaymentIntent uses idempotency key `pi-<type>-<bookingId>`; the refund uses `refund-<refundId>`.

**Uploads** (GEN-08, `references/backend.md` §11):
- JPG or PNG only, at most 5 MB each, random file names, stored on the server and served at `/uploads/<key>`.
- Documents store `ImageRef { _id, key }`; the URL is computed, never stored.
- Feature services enforce the counts (≤ 5 per post, activity or hotel; 1 airline logo).

**FX** (`references/domain-rules.md` §2):
- `convert` uses the newest rates document: `amount × rates[to] / rates[from]`, adjusted for each currency's `minorUnits` (JPY has 0), rounded half up.
- An unknown currency gives `400 UNSUPPORTED_CURRENCY`; no rates at all gives `503 RATES_UNAVAILABLE`.
- Responses carry `{ displayCurrency, rateDate }`.

**Reference data:**
- Dataset IDs are string `_id`s: airport `'CAI'`, city `'cairo'`, country `'EG'`, currency `'USD'`, attraction `'att-1'`.

# Execution — GEN-01: In-app notifications

Issue #19. Lane B of four lanes that run **at the same time** in separate folders. Stay inside the files listed in G4.

## Goal

Build the `notifications` module: it **listens to events** other modules emit and stores one notification per recipient, and it gives every logged-in user four endpoints: their list, their unread count, mark one as read, mark all as read. Today the module only registers its schema.

Done means:
1. A listener for each of the 10 notification events in the table below.
2. `GET /api/notifications`, `GET /api/notifications/unread-count`, `PATCH /api/notifications/:id/read`, `PATCH /api/notifications/read-all`.
3. Integration tests for the listeners and API tests for the endpoints.

**Out of scope:** emitting any event (bookings, payments, accounts and admin emit them in their own tickets), email (GEN-01b, issue #94), the frontend, CI, the data model.

## Context you need

**Requirement GEN-01 (verbatim):** "The system shall show in-app notifications (unread count, notification list, mark as read) for booking confirmation, cancellation and refund, flight schedule change, and account or provider suspension."

**Rules from the docs:**
- The module **listens to events**; no module calls it to notify (`domain-rules.md` §8, `data-model.md` §6.1: notifications calls no other module).
- Events: `backend/src/common/events/events.ts` (`Events.X`) and `event-payloads.ts` (`PayloadOf<typeof Events.X>`). Listen with `@OnEvent(Events.X)` from `@nestjs/event-emitter`; never a string literal. IDs arrive as strings.
- Lists are paginated, page size 10 (GEN-05): extend `PaginationQueryDto` usage and return `{ items, page, limit, total, totalPages }` (`backend/src/common/pagination/`: `paginate`, `toPage`, `Paginated`).
- JSON: IDs keep the field name `_id` (24-hex string), instants are ISO strings, enum values lowercase (`api-contract.md` §3).
- Access **User** = any logged-in account, every role (users, admins, moderators). Routes need no decorator: the global guards (from `AccountsModule`) already require a login. Read the user with `@CurrentUser() user: AuthUser` (`user.id` is the user's `_id`) from `backend/src/modules/accounts/auth/decorators.ts` / `auth.types.ts`.
- `:id` params use `ParseObjectIdPipe` from `@nestjs/mongoose` (as `blog.controller.ts` does): a malformed id answers **400 `VALIDATION_FAILED`**.
- Errors: `new NotFoundException({ code: ErrorCode.NotFound, message: 'Notification not found' })`.

**The schema exists, don't change it** (`backend/src/modules/notifications/schemas/notification.schema.ts`):
`userId` (ObjectId, recipient), `type` (`NotificationType` enum), `title` (≤ 100), `message` (≤ 500), `entity?` (`{ type, id }`, what to open), `readAt?` (null or absent = unread), timestamps; index `{ userId: 1, readAt: 1, createdAt: -1 }`. `{ readAt: null }` in a filter matches both null and a missing field, so it means "unread".

# Execution — PAY-01: Payments and Stripe webhook

Issue #21. First ticket of lane E (PAY-01 → PAY-02 → PAY-03, one after the other). **TDD is required**: the payment rule tests are committed, failing, before the rule code.

## Goal

A user pays for a `pending_payment` booking with Stripe (test mode). The backend creates or reuses one PaymentIntent per booking, the browser pays with the client secret (card data never reaches us), and **only Stripe's verified webhook** marks the payment succeeded and tells the booking modules (`payment.succeeded`). When a hold expires, the PaymentIntent is cancelled. Today the gateway bound to `STRIPE_GATEWAY` is a stub that throws `… implemented in PAY-01`, and there are no payment endpoints.

Done means:
1. A real `StripeGateway` (the only code that talks to Stripe), using the `stripe` package.
2. `POST /api/payments`, `POST /api/payments/:id/retry`, `GET /api/payments/:id`, `POST /api/payments/webhook`.
3. Webhook handling that is idempotent (a repeated or concurrent Stripe event is processed once), emits `payment.succeeded`, and records failures.
4. A listener that cancels the PaymentIntent when a flight booking or hotel reservation expires.
5. Unit, integration and API tests; no test ever calls Stripe.

**Out of scope:** the policies endpoints and storing acceptances (PAY-02; PAY-01 only *checks* that an acceptance exists), refunds and the `refund.*` webhook events (PAY-03; `createRefund` in the gateway is implemented now because the stub names PAY-01, but nothing calls it yet), confirming bookings (FLT-23, HTL-17 listen to `payment.succeeded`), multi-currency charging (after M1; every amount is the booking's currency, USD today), the frontend payment page (M2).

## Context you need

3. `decidePaymentStart(...)`.
4. `intent = await gateway.createPaymentIntent({ amountMinor: payable.amountMinor, currency: payable.currency, metadata: { bookingType, bookingId }, idempotencyKey })`. For `reuse` this is the same call with the same key: Stripe (and the fake) return **the same** PaymentIntent and client secret, so the client secret is never stored (PAY-01: only id, amount, currency, status).
5. `create`: insert `Payment { bookingType, bookingId, userId, stripePaymentIntentId: intent.id, amountMinor, currency, status: 'pending' }`. A duplicate-key error (another request for the same booking won the race) → load that payment and continue as `reuse`.
6. Return the session (`holdExpiresAt` from the payable).

**`retry(userId, paymentId): Promise<PaymentSession>`**, in this order:
1. The payment must be the user's (else 404 `'Payment not found'`).
2. Get the payable and run `decidePaymentStart` with this payment as `existing` and the acceptance check, **before** changing anything: `succeeded` → 409 `INVALID_STATUS_TRANSITION`, `canceled` or an expired hold → 409 `HOLD_EXPIRED`.
3. Only then: `failed` → conditional update `{ _id, status: 'failed' }` → `pending`; `pending` stays.
4. Return the session through `createPaymentIntent` with the same key.

**`get(userId, paymentId): Promise<PaymentView>`**: `{ _id, bookingType, bookingId, amountMinor, currency, status, createdAt }` of the user's payment, else 404.

**`handleWebhook(rawBody: Buffer | undefined, signature: string | undefined): Promise<void>`**:
1. Missing raw body or signature → 400 `BAD_SIGNATURE`. `event = gateway.parseWebhook(rawBody, signature)`.
2. `ignored`, `refund.updated`, `refund.failed` → return (PAY-03 handles refunds; log the type at debug level).
3. For `payment_intent.*`: in **one transaction** (`connection.transaction(async (session) => …)`): insert `StripeWebhookEvent { _id: event.id, type: event.type, receivedAt: now }` (`create([doc], { session })`), find the payment by `stripePaymentIntentId`, compute `next = paymentStatusAfter(event.type, payment.status)`, and if `next` isn't null update it conditionally on the status it was read with. No payment for that PaymentIntent → log a warning and finish (the event is still recorded as processed).
4. A duplicate-key error on the event (`code === 11000`) → already processed: return without doing anything (also on the retry the transaction helper makes after a write conflict).
5. **After the commit**, if the update moved the payment to `succeeded`, emit `Events.PaymentSucceeded { bookingType, bookingId }` (from the payment document, never from the event's metadata). Emit nothing otherwise.

Why the transaction: if the server crashes between "event recorded" and "payment updated", Stripe's retry would be treated as a duplicate and the payment lost. Recording both together, or neither, makes the retry safe.

**Expiry listener `payment-expiry.listener.ts`, `PaymentExpiryListener`** (a provider): `@OnEvent(Events.FlightBookingExpired)` and `@OnEvent(Events.HotelReservationExpired)`, each `async`, each inside `try/catch` that logs and never rethrows:
- find the payment for `{ bookingType, bookingId }`; none, or status `succeeded`/`canceled` → nothing;
- `pending`/`failed` → `await gateway.cancelPaymentIntent(id)`, then conditional update to `canceled` from the status it had;
- the gateway throws (e.g. the payment succeeded at the last second) → log a warning and leave the status: the `payment_intent.succeeded` webhook records it and the booking module refunds the late payment.

## Goal

Before paying, the user sees the provider's policies for **their booking** and ticks a checkbox. The backend shows the booking's policy snapshot and stores the acceptance with a timestamp. PAY-01 already blocks payment without an acceptance (`409 POLICIES_NOT_ACCEPTED`); today nothing can create one except a test.

Done means:
1. `GET /api/bookings/:type/:id/policies`: the booking's policy snapshot plus whether it was accepted and when.
2. `POST /api/bookings/:type/:id/accept-policies` `{ accepted: true }`: stores one `policy_acceptances` document per booking, idempotently, with the server's timestamp.
3. Accepting is refused for a booking that is already paid or whose hold is over.
4. Integration and API tests, including the end-to-end check "pay → 409, accept, pay → 201".

**Out of scope:** the real `getPolicies` implementations (flight-bookings FLT-08 / hotel-bookings HTL-09 implement the port; tests use `FakePayableBooking`), payments and the webhook (PAY-01, done), refunds (PAY-03), the summary page and checkbox UI (M2), changing `PaymentIntentsService` (it already checks acceptances).

## Design (settled here; follow it exactly)

1. **Where the logic lives:** a new internal service `PolicyAcceptancesService` (`policy-acceptances.service.ts`), provided by `PaymentsModule`, **not exported**, and a new controller `PoliciesController` (`policies.controller.ts`, `@ApiTags('payments') @Controller('bookings')`). Payments owns the routes even though the URL says `bookings`.
2. **Who may call:** `@Roles(Role.USER)` on both routes, as in PAY-01 (moderators and admins don't book). Ownership comes from the port: someone else's booking is a **404**, never a 403.
3. **GET works in every booking status** (the owner can re-read the policies of a confirmed or expired booking). It never writes.
4. **Accepting is allowed only while the booking can still be paid**, checked by a pure rule, in this order:
   | Booking status | Hold | Result |
   |---|---|---|
   | `confirmed` or `completed` | any | 409 `INVALID_STATUS_TRANSITION`, `'This booking is already paid'` |
   | `expired` or `cancelled` | any | 409 `HOLD_EXPIRED`, `'The hold has expired'` |
   | `pending_payment` | `holdExpiresAt` = now (exactly) | 409 `HOLD_EXPIRED` (the hold must be **after** now, as in PAY-01) |
   | `pending_payment` | now − 1 ms | 409 `HOLD_EXPIRED` |
   | `pending_payment` | now + 1 ms | allowed |
5. **Idempotent, first timestamp wins:** one acceptance per booking (the unique index). A repeated or concurrent accept returns the **existing** acceptance with its original `acceptedAt`; it never moves the timestamp. Implementation: one atomic upsert with `$setOnInsert` (never `$set`), and a duplicate-key error (two upserts racing) means "already accepted": read it and return it.
6. **The timestamp is the server's** (`new Date()` in the service). The body is exactly `{ accepted: true }`; `false`, a string, a missing field or any extra field is `400 VALIDATION_FAILED`. Ticking the box is the only thing the client says.
7. **Status code:** `POST …/accept-policies` answers **200** both the first time and on repeats (`@HttpCode(HttpStatus.OK)`), because it's an idempotent action on the booking, not the creation of a resource the client addresses later.
8. **Response shapes** (dates as ISO strings in JSON):
   - GET: the port's `BookingPolicies` flattened, plus `bookingId`, `accepted`, `acceptedAt`:
     - flight: `{ bookingType: 'flight', bookingId, segments: FlightSegmentPolicies[], accepted, acceptedAt }`
     - hotel: `{ bookingType: 'hotel', bookingId, cancellationTiers: PolicyTier[], checkInTime, checkOutTime, accepted, acceptedAt }`
     - `accepted: false` → `acceptedAt: null`.
   - POST: `{ bookingType, bookingId, accepted: true, acceptedAt }`.
   - Never return `userId` or the acceptance's `_id`.
9. **Wiring guard:** if the implementer returns policies whose `bookingType` differs from the route's `:type`, throw a plain `Error('PayableBooking for "<type>" returned "<other>" policies')` (a 500: a wiring bug, not a client error).

# Execution — PAY-03: Refunds

Issue #23. Third ticket of lane E (PAY-01 → PAY-02 → **PAY-03**). PAY-01 (#183) and GEN-01 (#168) are merged into `develop`. **TDD is required**: the refund rule tests are committed, failing, before the rule code.

## Goal

When a confirmed booking is cancelled with a positive refund (the user per the provider's tiers, the provider at 100%), or a payment arrives after the hold expired (`late_payment`, 100%), the booking module calls `PaymentsService.refund(...)` after its own transaction commits. Payments records one refund per booking, asks Stripe for it, follows its status through Stripe's webhook (`pending → refunded | failed`), shows it to the owner, and emits `refund.updated` so the user gets an in-app notification (GEN-01 already listens). Today both `PaymentsService` methods throw `… implemented in PAY-03`, and refund webhook events are ignored.

Done means:
1. `PaymentsService.refund` and `PaymentsService.getRefund` work (same public signatures; `FakePaymentsService` stays valid).
2. `refund.updated` / `refund.failed` webhook events update the refund, idempotently, in the same style as PAY-01's payment events.
3. `GET /api/refunds/:id` shows a refund to its owner.
4. `refund.updated { refundId, userId, status }` is emitted after every stored status, so the user is notified.
5. Unit, integration and API tests; no test calls Stripe.

**Out of scope:** computing refund amounts or tiers (each booking module owns its tier rule, `DECISIONS.md` §3), cancelling bookings (FLT-26, FLT-06, HTL-21), deciding a payment is late (FLT-23, HTL-17 already call `refund` with `reason: 'late_payment'`), showing the refund on booking details (the booking modules call `getRefund`), retrying a failed refund automatically, partial or multiple refunds per booking, the frontend.

## Design (settled here; follow it exactly)

1. **Where the logic lives:** a new internal `RefundsService` (`refunds.service.ts`), provided by `PaymentsModule`, **not exported**. `PaymentsService` gets a constructor that injects it, and its two methods just delegate (`return this.refunds.refund(request)` / `return this.refunds.getRefund(bookingType, bookingId)`). The public API, and so `FakePaymentsService`, doesn't change. A new `RefundsController` (`refunds.controller.ts`, `@ApiTags('payments') @Controller('refunds')`) serves `GET /api/refunds/:id`.

2. **`refund(request)` order** (each step only if the previous passed):
   1. `amountMinor` must be a safe integer > 0 → else 400 `VALIDATION_FAILED`, field `amountMinor`, message `'must be greater than 0'` (the fake's exact details). No database read happens before this check.
   2. A refund already exists for `{ bookingType, bookingId }` → return its view. **No other check, no Stripe call, no emit.** (The contract: "a second call for the same booking returns the existing one", whatever the new arguments are.)
   3. Load the booking's payment (`{ bookingType, bookingId }`) and run the pure check of Design §3.
   4. Insert `Refund { paymentId, bookingType, bookingId, userId, amountMinor, currency, reason, status: 'pending' }`. A duplicate key (another call won the race) → load that refund and return its view: **no Stripe call, no emit** from the loser.
   5. `gateway.createRefund({ paymentIntentId: payment.stripePaymentIntentId, amountMinor, idempotencyKey: `refund-${refundId}`, metadata: { refundId } })`.
      - Success → `status = refundStatusFromGateway(result.status)`; conditional update `{ _id, status: 'pending' }` → `$set { stripeRefundId: result.id, status }`. (If the update matches nothing, a webhook already moved it: reload and use the stored status.)
      - The gateway throws → conditional update `{ _id, status: 'pending' }` → `failed`; log a warning with the refund id and the error message only; **don't rethrow**. The caller's cancellation is already committed; the refund is visible as `failed`, never lost.
   6. Emit `Events.RefundUpdated { refundId, userId, status }` with the stored status, **after** the writes, exactly once per `refund()` call that created the document.
   7. Return the view (`RefundView`).

3. **The pure request check** (`refund-rules.ts`, TDD), in this order:
   | Case | Result |
   |---|---|
   | no payment for the booking | 409 `INVALID_STATUS_TRANSITION`, `'The booking has no succeeded payment'` |
   | payment status `pending`, `failed` or `canceled` | the same 409 |
   | payment `succeeded`, `request.amountMinor > payment.amountMinor` | 400 `VALIDATION_FAILED`, field `amountMinor`, `'must not exceed the amount paid'` |
   | `request.amountMinor === payment.amountMinor` | allowed (a 100% refund) |
   | `request.currency !== payment.currency` | 400 `VALIDATION_FAILED`, field `currency`, `'must match the payment currency'` |
   | `request.userId !== payment.userId` (as strings) | 400 `VALIDATION_FAILED`, field `userId`, `'must be the payer'` |
   | everything matches | allowed |
   A late payment needs no special case: PAY-01 records a late `payment_intent.succeeded` on a canceled payment as `succeeded`.

4. **Gateway status → our status** (`refundStatusFromGateway`, TDD): `succeeded` → `refunded`; `failed`, `canceled` → `failed`; `pending`, `requires_action` → `pending`.

5. **Webhook transitions** (`refundStatusAfter(gatewayStatus, current) → RefundStatus | null`, TDD; null = leave it):
   | Gateway status \ current | `pending` | `refunded` | `failed` |
   |---|---|---|---|
   | `succeeded` | `refunded` | null | `refunded` |
   | `failed`, `canceled` | `failed` | `failed` (Stripe can fail a refund after it succeeded) | null |
   | `pending`, `requires_action` | null | null | null |

6. **Webhook handling** (`RefundsService.handleWebhookEvent(event)` for the refund branch of `GatewayEvent`):
   - In **one** `connection.transaction`: insert `stripe_webhook_events { _id: event.id, type: event.type, receivedAt }`; find the refund by `stripeRefundId: event.refund.id`, else (Stripe's event can arrive before step 2.5's update is stored) by `_id: event.refund.metadata.refundId` when that is a 24-hex string; none → log a warning and finish (the event stays recorded). `next = refundStatusAfter(event.refund.status, refund.status)`. Conditional update `{ _id, status: <read status> }` → `$set { status: next, stripeRefundId: event.refund.id }` when `next` isn't null; when `next` is null but `stripeRefundId` is missing, set only `stripeRefundId`.
   - A duplicate key on the event → already processed: return (also on the helper's retry after a write conflict, as PAY-01 does).
   - After the commit, if the status changed: emit `Events.RefundUpdated { refundId, userId, status: next }` (ids from the refund document, never from the event).
   - In `PaymentIntentsService.handleWebhook`, the only change: where it now returns for non-payment events, call `await this.refunds.handleWebhookEvent(event)` for `refund.updated` / `refund.failed` and keep the debug log + return for `ignored`. Inject `RefundsService` into `PaymentIntentsService`. Nothing else in that file changes.

7. **`GET /api/refunds/:id`:** `@Roles(Role.USER)`; the refund must have `userId` = the caller, else 404 `'Refund not found'`. Returns `RefundView` (never `paymentId`, `userId`, `stripeRefundId`).

8. **No automatic retry of a failed refund** in PAY-03. A second `refund()` call returns the failed one unchanged (Design §2.2). Flag this in the report and the PR.
