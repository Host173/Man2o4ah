````markdown
### 4.1 `SeatInventory` (flights module)
`items` = list of `{ flightId, cabinId, seats }`. Every update matches the cabin with `$elemMatch` and changes it with the positional `$`, so check + change happen in **one atomic document update**.

| Method | Filter (besides `_id` and cabin `_id`) | Change | Fails with |
|---|---|---|---|
| `hold(items)` | flight `status: scheduled`, `departureAt > now`; cabin `availableSeats ≥ seats` | `availableSeats −seats`, `heldSeats +seats`, `hasBookings = true` | `SeatsUnavailable` |
| `confirm(items)` | cabin `heldSeats ≥ seats` | `heldSeats −seats`, `bookedSeats +seats` | `InventoryCorrupted` |
| `release(items)` | cabin `heldSeats ≥ seats` | `heldSeats −seats`, `availableSeats +seats` | `InventoryCorrupted` |
| `returnBooked(items)` | cabin `bookedSeats ≥ seats` | `bookedSeats −seats`, `availableSeats +seats` | `InventoryCorrupted` |
| `changeCapacity(flightId, cabinId, newTotal, expectedTotal)` | cabin `totalSeats = expectedTotal`, `availableSeats ≥ expectedTotal − newTotal` | `totalSeats` and `availableSeats` both `+ (newTotal − expectedTotal)` | `CapacityBelowReserved` or `ConcurrentChange` |

Example (`hold`, one item):
```js
flights.updateOne(
  { _id: flightId, status: 'scheduled', departureAt: { $gt: now },
    cabins: { $elemMatch: { _id: cabinId, availableSeats: { $gte: seats } } } },
  { $inc: { 'cabins.$.availableSeats': -seats, 'cabins.$.heldSeats': seats },
    $set: { hasBookings: true } },
  { session })
// modifiedCount === 0  →  throw SeatsUnavailable
```
A round trip holds both segments in the same transaction, so it never holds one without the other.
````

                                         Database Design · Team Review · 2/24
The seven rules
  1   One owner per collection
      Each collection belongs to one module. Other modules use that module's service, never its
      collection, and never populate across modules.


 2    Embed what a parent owns; reference what is shared
      Cabins live inside a flight, passengers inside a booking, days inside an itinerary. Flights,
      rooms, users and airports are referenced by ID.


 3    A hold is a pending booking
      Proceeding to payment creates a pending_payment booking that keeps the inventory for 10
      minutes. Payment confirms it; the timeout expires it.


 4    The database guarantees no overselling
      Seats: one atomic "take N only if N are free" update. Rooms: one document per room per
      night with a unique index.


 5    Bookings keep snapshots
      Prices and policies are copied at hold time, so later edits by moderators never change an
      existing booking or its refund.


 6    Money is integers, times are UTC
      Prices are whole cents in one platform currency (USD). Instants are UTC; calendar dates are
      midnight UTC; flight times are shown in the airport's local time.


 7    Modules talk through services, ports and events
      Lower modules never import higher ones. When they must, the lower module owns an
      interface (port) or emits an event.

reference-data                                                                             GEN-12, FLT-02

Holds the course datasets (countries, cities, airports, attractions) and the supported currencies.
The graders test the API in Swagger using these exact IDs.
 countries                       8 countries, each with its currency
 cities                          8 cities
 airports                        8 airports with IANA time zones
 attractions                     8 attractions
 currencies                      7 supported currencies, derived from the countries file

WHY IT IS DESIGNED THIS WAY
 The dataset ID is the document's _id ( 'CAI' , 'cairo' , 'EG' ). A grader can type an ID from the
 CSV into Swagger and it just works. Other modules store these IDs as plain strings.
 Read-only. No endpoint writes to these collections, so no feature can corrupt the data the graders
 rely on.
 Currencies come from the countries file. GEN-12 asks us to seed supported currencies; the dataset
 already names one per country. Each currency stores its minorUnits (JPY has none).
TRICKY PARTS
  The seed must import rows exactly, be safe to re-run (upsert by _id ), and check every reference
  before writing anything.
  Airport time zones drive every flight time in the system (FLT-03, GEN-06).
HOW IT TALKS TO OTHER MODULES
Read by accounts, flights, hotels, itineraries and fx through its service.
POSSIBLE FUTURE CONFLICTS
  If the course publishes new CSVs, re-run the seed. The seed never deletes, so removing a row that
  is already used can't break anything silently.




                                            Database Design · Team Review · 5/24
accounts                                                                          ACC-01 – ACC-19, GEN-13

Who you are and what you may do: registration, login, lockout, sessions, profile, roles, and which
provider a moderator manages.
 users                         every account: users, admins, airline and hotel moderators
 sessions                      one per logged-in device; refresh token hash and idle expiry

WHY IT IS DESIGNED THIS WAY
 One users collection for every role, with a role field. One login flow, one lockout rule, one
 password rule.
 Moderator assignment is embedded ( moderatorOf ) because a moderator manages exactly one
 provider (ACC-13).
 A sessions collection is needed because logout must revoke the refresh token on the server and
 sessions expire after 30 idle minutes (ACC-06). A TTL index deletes expired sessions automatically.
TRICKY PARTS
  Lockout counter must be atomic ( $inc ). Read-then-write lets five parallel wrong passwords slip
  past the limit.
  Every authenticated request checks the session and slides its expiry. Password change, admin reset,
  suspension and deactivation delete all the user's sessions.
  Deactivation is blocked while the user has upcoming confirmed bookings (ACC-12), but accounts
  can't import the booking modules (that would be a cycle). So accounts defines an
  ActiveBookingsCheck port and the booking modules implement it.
  Tokens live only in httpOnly cookies (ACC-19). Nothing auth-related goes to localStorage.
HOW IT TALKS TO OTHER MODULES
Emits user.deactivated , user.reactivated , account.suspended , account.reactivated . Its auth
guards are used by every module.
POSSIBLE FUTURE CONFLICTS
  The auth guard and the role/ownership guards are needed by everyone, so they must be built first, in
  the shared foundation.
  Bonus email verification would add fields (for example emailVerifiedAt ). That is an additive
  change.




                                        Database Design · Team Review · 6/24
flights                                                                          FLT-01 – FLT-17, FLT-30, GEN-06

The airline moderator's world: airline profile, baggage and cancellation policies, flights, cabins,
and the seat inventory.
 airlines                       profile, logo, active flag, baggage policy, cancellation tiers
 flights                        schedule, status and embedded cabins with seat counters

WHY IT IS DESIGNED THIS WAY
 Cabins are embedded in the flight. A flight has at most 4, and they never exist alone. Because the
 seat counters live inside one document, "take 3 seats only if 3 are free" is one atomic update. That
 is what makes overselling impossible (FLT-22).
 Four counters per cabin: total, available, held, booked, always total = available + held + booked .
 Search shows available seats directly (FLT-11), and a capacity cut can be checked in the same
 atomic way (FLT-05).
 Times are stored in UTC, plus departureLocalDate (the date at the departure airport). Search by
 local date and the "same flight number on the same date" rule become simple equality checks.
 Policies are embedded in the airline: there is one of each, and they're always read with it.
  hasBookings flag: airports can't change once a flight is booked (FLT-05). The flag is set when seats
 are first held, so flights never has to ask flight-bookings, which would be a cycle.
TRICKY PARTS
   SeatInventory is the only code that changes seat counters. Every hold, confirm, release,
  cancellation and capacity change goes through it.
  Time zones: local input → UTC, and departureLocalDate recomputed whenever the time changes.
  Cancelling a flight (FLT-06) must cancel its bookings with a 100% refund, but flights doesn't own
  bookings. It emits flight.cancelled and flight-bookings does the rest.
HOW IT TALKS TO OTHER MODULES
Emits flight.rescheduled , flight.cancelled . Used by flight-bookings ( SeatInventory , flight details)
and itineraries (search reuse, ITN-26).
POSSIBLE FUTURE CONFLICTS
  The flight-bookings owner builds on SeatInventory . Its method list (data model §4.1) is the contract
  between the two owners; agree on it before either starts.




                                         Database Design · Team Review · 7/24
flight-bookings                                                                FLT-12, FLT-19 – FLT-29, GEN-11

A traveler's flight bookings: passengers, baggage, the seat hold, confirmation, e-ticket and
cancellation.
 flight_bookings                booking with embedded segments (1–2), passengers, pricing, policy
                                snapshot and status

WHY IT IS DESIGNED THIS WAY
 A hold is a pending_payment booking. FLT-22 says the hold creates a booking in Pending Payment,
 and GEN-11 starts the lifecycle there. A separate holds collection would duplicate that state.
 Segments and passengers are embedded: they belong to the booking and are bounded.
 Snapshots. The fare and the airline's policies are copied into the booking at hold time. A later price
 change doesn't touch it (FLT-05), and refunds use the policy the user actually accepted (PAY-02).
 Synced copies of departure times let us list Upcoming/Past and check "before departure" without
 querying another module. They're updated by the flight.rescheduled event.
 The reference is set on confirmation (FLT-23). A partial unique index lets many pending bookings
 have none.
TRICKY PARTS
  Booking and seat counters change in one transaction, so a crash can't leave seats held with no
  booking. A round trip holds both segments or nothing.
  The expiry job and the payment webhook can hit the same booking at the same moment. Both use
  a conditional update ("only if still pending_payment "), so exactly one wins.
  A payment that succeeds after expiry must not confirm; it gets a full automatic refund.
  Passenger type is checked against age on the departure date. Infants take no seat and pay 10%.
  Extra baggage is charged per segment at that airline's price.
  FLT-29 (bookings per flight, passenger CSV) lives here even though its URL starts with /flights ,
  because only this module can read bookings.
HOW IT TALKS TO OTHER MODULES
Uses flights ( SeatInventory ) and payments (refunds). Implements the PayableBooking and
ActiveBookingsCheck ports. Listens to payment.succeeded , flight.rescheduled , flight.cancelled .
Emits confirmed / cancelled / expired / rescheduled events.
POSSIBLE FUTURE CONFLICTS
  Agree on the PayableBooking port and the payment.succeeded payload with the payments owner
  first.
  The admin booking list (ACC-17) reads from here through the service.

                                                                                                                        Database Design · Team Review · 9/24
hotels                                                                                          HTL-01 – HTL-15

The hotel moderator's world: hotel profile, policies, rooms, availability, blocked dates, and the
room-night inventory.
 hotels                          profile, photos, amenities, times, cancellation tiers, rating summary
 rooms                           bookable units with price, occupancy and availability ranges
 room_nights                     one document per taken room per night (reserved or blocked)

WHY IT IS DESIGNED THIS WAY
  room_nights is the double-booking guarantee. One document per room per night, with a unique
 index on (room, date). Two reservations for the same night can't both be saved, even at the exact
 same millisecond. Date-range overlap checks in code can't promise that.
 Blocked dates use the same documents ( kind: blocked ), so a block and a reservation also can't
 overlap (HTL-06).
 Rooms are their own collection, not embedded in the hotel: reservations and nights point to them,
 and search queries them across hotels.
 Availability ranges stay on the room (few, small). The room's inventoryVersion is bumped by every
 inventory change, so two changes to the same room in parallel conflict and one retries.
  ratingSummary is stored on the hotel for the rating filter and sort (HTL-12). It's updated only through
  HotelsService.setRatingSummary .

TRICKY PARTS
  Date semantics: a stay from the 10th to the 13th uses the nights of the 10th, 11th and 12th. Availability
  ranges are inclusive.
  Search (HTL-11): a hotel qualifies if it has enough free rooms for the whole stay and their combined
  occupancy covers the guests. The price filter uses the cheapest qualifying room.
  Editing availability, deactivating or deleting a room must check reservations from today onward,
  inside the same transaction.
HOW IT TALKS TO OTHER MODULES
Used by hotel-bookings ( RoomNightInventory , room details, setRatingSummary ) and itineraries (search
reuse, ITN-25).
POSSIBLE FUTURE CONFLICTS
  RoomNightInventory 's method list (data model §4.2) is the contract with hotel-bookings.
  HTL-08 (room status view) and HTL-22 (hotel's reservations) live in hotel-bookings, because they
  need reservation data.

hotel-bookings                                                                            HTL-16 – HTL-24

Reservations (one or more rooms in one hotel) and reviews.
 hotel_reservations             reservation with embedded rooms, guests, price and policy snapshots
 reviews                        one rating and review per completed reservation

WHY IT IS DESIGNED THIS WAY
 Same pattern as flights: a hold is a pending_payment reservation, rooms and guests are embedded,
 prices and policies are snapshots.
 Reviews are their own collection, because they're listed per hotel, newest first, paginated (HTL-24).
 The unique index on reservationId enforces one review per reservation, however many rooms it
 had.
TRICKY PARTS
  All selected rooms are held together or not at all (HTL-16, HTL-18): one transaction, any unavailable
  room rejects the whole request.
  Refund on the full total, only before the check-in date, never partial (HTL-21).
  Every review change recomputes the hotel's rating, including an admin hiding or deleting a review.
HOW IT TALKS TO OTHER MODULES
Uses hotels and payments. Implements PayableBooking , ActiveBookingsCheck and ReportableContent
(reviews). Listens to payment.succeeded . Emits confirmed / cancelled / expired events.
POSSIBLE FUTURE CONFLICTS
  Shares the PayableBooking port with flight-bookings. Keep both implementations identical in
  behaviour.

                                                                                                                               Database Design · Team Review · 12/24
payments                                                                                  PAY-01 – PAY-04

Money in and out through Stripe test mode: PaymentIntents, the webhook, refunds, and policy
acceptance.
 payments                       one PaymentIntent per booking
 refunds                        one refund per cancelled booking
 policy_acceptances             when the user accepted the policies
 stripe_webhook_events          IDs of processed webhook events

WHY IT IS DESIGNED THIS WAY
 Store only what PAY-01 allows: Stripe ID, amount, currency, status. Card data never reaches us.
 One payment per booking. A failed card retries on the same PaymentIntent.
 Bookings are confirmed only by the verified webhook, never by the frontend saying "it worked".
  stripe_webhook_events makes the webhook idempotent: Stripe can send the same event twice, and
 we process it once.
 Payments doesn't import the booking modules. It defines a PayableBooking port (amount, status,
 hold expiry) and emits payment.succeeded . That avoids a dependency cycle.
TRICKY PARTS
  Webhook signature verification needs the raw request body.
  When a hold expires, the PaymentIntent is cancelled. A late success still triggers a full refund.
  A refund document is created only when the amount is above 0 (PAY-03), and its status is updated
  from Stripe.
HOW IT TALKS TO OTHER MODULES
Called by both booking modules for refunds. Emits payment.succeeded and refund.updated . Listens to
booking expiry events.
POSSIBLE FUTURE CONFLICTS
  Its two ports/events are the contract with both booking owners. Write them first, then all three can
  work in parallel against fakes.

Glossary
Embedded                     Stored inside the parent document. Loaded, saved and deleted with it.
Reference                    A field holding another document's ID. MongoDB doesn't check it; the service
                             does.
Snapshot                     A copy of a value at a moment (price, policy) that never changes afterwards.
Hold                         A pending_payment booking that keeps inventory for 10 minutes.
Transaction                  Several writes that all succeed or all fail together.
Atomic update                A check and a change done by the database in one step, so nothing can happen in
                             between.
Unique index                 The database rejects a second document with the same values.



                                             Database Design · Team Review · 23/24
Partial index   An index that only covers documents matching a condition (e.g. those that have a
                reference).
TTL index       The database deletes documents automatically after a date.
Port            An interface a module owns and another module implements, so the first doesn't
                depend on the second.
Event           A message one module emits ("payment succeeded") and others react to without
                being called directly.
Minor units     Money as whole cents (1999 = $19.99), so there are no rounding errors.
